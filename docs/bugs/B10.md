# B10: A frozen worker wakes up and writes stale data

- **Switched on by:** `payments.dedupe: check-then-insert`. The bug-free value is `claim-first`.
- **Scan pattern:** none, on purpose.
- **Code:** [PaymentService.java](../../demo-app/src/main/java/dev/faultline/demo/payment/PaymentService.java)
- **Plan:** [b10.plan.yaml](../../benchmark/b10.plan.yaml)

## The bug

The worker checks whether a payment is done, then acts:

```java
case CHECK_THEN_INSERT -> {
    if (alreadyProcessed(p)) return;
    apply(p);
    markProcessed(p);
}
```

A worker that freezes mid-payment for long enough loses its partition to another worker, which applies the same
payment. When the frozen worker wakes up, it applies the payment again. There is no code pattern for this on purpose.

## How Faultline proves it

Freeze worker-1 for 15s just before it applies its 200th payment. The demo app takes a worker out of the group
after 10s. 2,000 payments.

The check that fails is `no-duplicates`.

## Evidence

| Run | Fault fired | What the check found |
|---|---|---|
| run-1 | 1 of 1 freezes | pay-42-683 applied twice |
| run-2 | 1 of 1 freezes | pay-42-683 applied twice |
| baseline | none | each payment once |

Confirmed: the check failed in 2 of 2 runs with the fault, and passed in the baseline. On the bug-free build, the same plan came out suspected: the fault fired in both runs and every check passed.

## The fix

Claim first (`payments.dedupe: claim-first`). The second worker's claim waits on the first one's row, then finds
it taken and skips.

Rerun: `./faultline benchmark --bug B10`
