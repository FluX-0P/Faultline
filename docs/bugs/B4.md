# B4: Read-modify-write on the balance

- **Switched on by:** `payments.merchant-balance: read-then-write`. The bug-free value is `locked`.
- **Scan pattern:** P4, flagged at its location.
- **Code:** [MerchantBalance.java](../../demo-app/src/main/java/dev/faultline/demo/payment/MerchantBalance.java)
- **Plan:** [b4.plan.yaml](../../benchmark/b4.plan.yaml)

## The bug

Every payment credits the shop by reading its balance, then writing it back plus the amount:

```java
void credit(long amountMinor) {
    write(read() + amountMinor);
}
```

Two workers can read the same balance. The second write then undoes the first worker's credit.

## How Faultline proves it

Hold worker-1 after `MerchantBalance#read`, on every 5th call, 3 times, until another worker has returned from
`MerchantBalance#write`. Faultline waits up to 3s. 100 payments go out 200ms apart, so without the barrier no two
overlap.

The check that fails is `shop-balance-adds-up`.

## Evidence

| Run | Fault fired | What the check found |
|---|---|---|
| run-1 | 3 of 3 barriers | shop balance 243,272, payments add up to 252,444 |
| run-2 | 3 of 3 barriers | the same |
| baseline | none | the balance adds up |

Confirmed: the check failed in 2 of 2 runs with the fault, and passed in the baseline. On the bug-free build, the same plan came out suspected: the fault fired in both runs and every check passed.

## The fix

Lock the row on the read (`payments.merchant-balance: locked`): `select ... for update`. The next worker waits,
then reads the new balance, and the barrier gives up after 3s.

Rerun: `./faultline benchmark --bug B4`
