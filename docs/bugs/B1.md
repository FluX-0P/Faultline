# B1: Saves, then acknowledges the message

- **Switched on by:** `payments.dedupe: none`. The bug-free value is `claim-first`.
- **Scan pattern:** P1, flagged at its location.
- **Code:** [PaymentService.java](../../demo-app/src/main/java/dev/faultline/demo/payment/PaymentService.java)
- **Plan:** [b1.plan.yaml](../../benchmark/b1.plan.yaml)

## The bug

The worker commits the payment, then acknowledges its Kafka message. With no duplicate check, a message Kafka
delivers again is applied again.

```java
service.process(event);   // commits the payment
ack.acknowledge();        // a crash before this line: Kafka delivers the message again
```

`PaymentService#process` with `payments.dedupe: none` calls `apply(p)` with no check, so the redelivered payment is
charged and recorded twice.

## How Faultline proves it

Crash worker-1 just before it acknowledges a message, on every 150th acknowledgment, twice; 3,000 payments at 100/s.

The check that fails is `no-duplicates`.

## Evidence

| Run | Fault fired | What the check found |
|---|---|---|
| run-1 | 2 of 2 crashes, 2 restarts | 2 payments applied twice: pay-42-519, pay-42-2233 |
| run-2 | 2 of 2 crashes, 2 restarts | 2 payments applied twice: pay-42-519, pay-42-1952 |
| baseline | none | no-duplicates passed: 3,000 payments, each once |

Confirmed: the check failed in 2 of 2 runs with the fault, and passed in the baseline. On the bug-free build, the same plan came out suspected: the fault fired in both runs and every check passed.

## The fix

Claim the payment first, in the same transaction (`payments.dedupe: claim-first`). A redelivered message finds
its claim and is skipped:

```java
case CLAIM_FIRST -> {
    if (markProcessed(p) == 0) return;   // insert ... on conflict do nothing
    apply(p);
}
```

Rerun: `./faultline benchmark --bug B1`
