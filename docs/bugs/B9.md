# B9: A retry topic reorders events for one account

- **Switched on by:** `payments.retries: retry-topic`. The bug-free value is `in-place`.
- **Scan pattern:** none, on purpose.
- **Code:** [PaymentListener.java](../../demo-app/src/main/java/dev/faultline/demo/payment/PaymentListener.java)
- **Plan:** [b9.plan.yaml](../../benchmark/b9.plan.yaml)

## The bug

A payment that fails is retried later from another topic:

```java
} catch (RuntimeException e) {
    if (!retryTopic) throw e;
    kafka.send(TopicConfig.PAYMENTS_RETRY, event.accountId(), payload).get();
}
```

Later payments for the same account overtake it. There is no code pattern for this on purpose: only breaking the app
finds it.

## How Faultline proves it

Make worker-1 fail every 100th payment, 4 times, as a passing database error would; 2,000 payments. per-key-order
counts only payments that happened one after the other. These numbers are from B9's own benchmark run after the change
to 4 failures, the same day and seed.

The check that fails is `per-key-order`.

## Evidence

| Run | Fault fired | What the check found |
|---|---|---|
| run-1 | 4 of 4 failures | 11 payments applied before an earlier one for the same account, such as acct-13 |
| run-2 | 4 of 4 failures | 2, such as acct-28: pay-42-1883 applied before pay-42-1715 |
| baseline | none | every account in order |

Confirmed: the check failed in 2 of 2 runs with the fault, and passed in the baseline. On the bug-free build, the same plan came out suspected: the fault fired in both runs and every check passed.

## The fix

Retry in place (`payments.retries: in-place`). The error handler retries the payment before any later one on its
partition, so the order for each account holds.

Rerun: `./faultline benchmark --bug B9`
