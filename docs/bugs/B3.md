# B3: Dedupes by message ID only, so a double submit slips through

- **Switched on by:** `payments.dedupe-key: event-id`. The bug-free value is `payment-id`.
- **Scan pattern:** P3, flagged at its location.
- **Code:** [PaymentService.java](../../demo-app/src/main/java/dev/faultline/demo/payment/PaymentService.java)
- **Plan:** [b3.plan.yaml](../../benchmark/b3.plan.yaml)

## The bug

The worker marks what it processed by the event ID the API gives each submission, not by the payment:

```java
private String key(PaymentEvent p) {
    return byEventId ? p.eventId() : p.paymentId();
}
```

A client that submits the same payment twice gets two event IDs, so both are applied and charged.

## How Faultline proves it

Send every 50th request twice, like a client that submits again, 20 times; 2,000 payments.

The check that fails is `one-charge-per-payment`.

## Evidence

| Run | Fault fired | What the check found |
|---|---|---|
| run-1 | 20 of 20 double submits | 20 payments applied and charged twice: pay-42-49, -99, -149 ... |
| run-2 | 20 of 20 double submits | the same 20 |
| baseline | none | one charge per payment |

Confirmed: the check failed in 2 of 2 runs with the fault, and passed in the baseline. On the bug-free build, the same plan came out suspected: the fault fired in both runs and every check passed.

## The fix

Dedupe by the payment ID, which both submissions share (`payments.dedupe-key: payment-id`).

Rerun: `./faultline benchmark --bug B3`
